## 1. What changed and why

### 1.1 The problem

Images reached the browser through several paths, and three of them moved far
more data than the page actually needed.

| Path | Before | After |
|---|---|---|
| Gallery card preview | `/api/images/<id>/processed` — full processed image | `/api/images/<id>/processed/thumb` — cached ≤320px preview |
| `/api/detection/<id>` (modal) | base64 of **both** full images in the JSON, which the modal JS then ignored in favour of `*_image_url` | URLs only; the two base64 fields are empty strings |
| `/api/images/<id>` (metadata) | whole document read, ~120 KB of binaries discarded | projected to the 4 metadata fields actually returned |

The modal case was the worst: every card click transferred the original image
**twice** — once base64-encoded inside the JSON (≈33% larger again) and once
more through the image URL.

### 1.2 Implementation

**`ealpr/image_thumbnails.py`** (new) — a small, self-contained module:

- `sniff_image_mime()` — identifies JPEG/PNG/GIF/BMP/TIFF/WEBP from magic
  bytes, so responses are typed from actual content rather than a hardcoded
  `image/jpeg`. Returns `None` for anything that is not an image.
- `build_thumbnail()` — resizes with `Image.thumbnail()` (never enlarges,
  always preserves aspect ratio), honours EXIF orientation, flattens
  palette/alpha/grayscale modes so JPEG encoding cannot fail.
- `get_or_create_thumbnail()` — returns cached bytes if present, otherwise
  generates and caches. **Never raises**: missing, empty, truncated, corrupt
  and unsupported inputs all return `None` so the caller degrades instead of
  returning a 500.
- `read_cached_thumbnail()`, `thumbnail_cache_path()`, `thumbnail_cache_stats()`.

**Cache design — deliberately not a database field.** Thumbnails are a derived,
disposable on-disk cache under `detected_plates/thumbnails/`:

- **No MongoDB schema change**, so no migration and no risk to the existing
  `BinaryField` image data.
- Deleting the directory at any time is safe; the next request regenerates it.
- Writes are atomic (temp file + `os.replace`), and a failed write still
  returns the freshly generated bytes, so a read-only or full disk degrades
  performance rather than breaking image delivery.
- The cache is keyed by `detection id + image type + box size`. Detection images
  are immutable once written, so an entry cannot go stale. (A detection's
  images are never replaced in place.)
- A cache hit is answered **without touching MongoDB at all** — verified: zero
  queries on a hit.

**`ealpr/blueprints/detection.py`**

- New `GET /api/images/<id>/<type>/thumb`, authenticated, same cache headers.
- Full-image endpoint now projects only the two fields it needs, sniffs the
  real MIME type, uses `send_file(..., conditional=True)`, and validates
  `img_type` against an allowlist (`400` for anything else).
- `/api/detection/<id>` and `/api/images/<id>` project the binaries away.
- Both endpoints log the real exception server-side and return a generic
  message, so filesystem paths and driver errors are never sent to a client.
  (Previously a 500 body could contain `str(e)`.)

**`config.py`** — `THUMBNAIL_DIR`, `THUMBNAIL_SIZE = (320, 320)`,
`THUMBNAIL_QUALITY` (env-overridable, default 80).

**`ealpr/__init__.py`** — `detection_thumb_url` now returns the thumbnail URL.
The older `detection_thumb` filter is left intact for any other caller.

**Templates** — `uploaded_images.html` gallery cards use the thumbnail filter
and keep `loading="lazy"` / `decoding="async"`. A placeholder
(`static/img/image-unavailable.svg`, 601 B) is wired through `onerror` on
gallery cards and on the modal images in both `uploaded_images.html` and
`detection_history.html`, with `this.onerror=null` first so a missing
placeholder cannot loop.

**`requirements.txt`** — `Pillow>=10.0.0` added explicitly. Pillow 11.2.1 was
already installed transitively via Ultralytics, but Block B now imports it
directly, so relying on a transitive dependency would be fragile.

### 1.3 What was deliberately *not* done

- No MongoDB schema change, no data migration, no deletion or rewriting of any
  stored image.
- No change to Block A behaviour (pagination, filtering, lazy loading,
  dashboard polling) — all 21 Block A regression checks still pass.
- No service worker, no CDN work, no authentication redesign.
- `detection_history.html` has no inline preview thumbnails: its table shows
  metadata only, and the only images it loads are the explicit modal
  originals/processed. Adding previews there would be new UI scope, so the
  change was limited to failure handling.

### 3.2 Thumbnail module — 40 passed, 0 failed

- Magic-byte MIME detection for 6 formats; correctly rejects plain text, empty
  input, truncated magic bytes, and `RIFF` containers that are not WEBP.
- Geometry: portrait 1080×1920 → 180×320; landscape 1600×900 → 320×180;
  aspect ratio preserved in both; a 100×80 source is **not** upscaled.
- PNG-with-alpha and grayscale sources convert to viewable JPEGs.
- Corrupt input (6 variants incl. JPEG magic + junk, truncated PNG, random
  bytes, `None`, empty) → `None`, no exception; a valid image still succeeds
  immediately afterwards.
- Cache: created on first call, byte-identical on repeat, **file never
  rewritten** (mtime stable), separate entries per image type, filesystem-safe
  filenames, regenerates after deletion, and **a hit is answerable with no
  source at all**. An unwritable cache directory still serves the image.

### 3.3 HTTP layer — 81 passed, 0 failed

Run against the real Flask app with a controlled stand-in for the data layer,
so routing, MIME handling, caching, headers, auth and error paths all execute
for real. Only the infrastructure state (DB-online flag, identity lookup) was
stubbed, because Atlas had no primary.

- Full image: binary-backed and path-backed records return 200 with **byte-exact**
  content; a PNG stored in MongoDB is served as `image/png`; a record whose
  path points at a deleted file → 404; a record with no image → 404.
- Errors: malformed id → 400, unknown id → 404, unknown image type → 400,
  encoded path traversal refused. No traceback, driver name, site-packages
  path or Windows path appears in any error body.
- Thumbnail: 200, real JPEG, bounded to 320, aspect preserved, PNG source
  yields a JPEG thumb. Corrupt / not-an-image / empty → **404, never 500**.
- Cache over HTTP: 6 repeat requests never rewrite the file; **a hit performs
  zero database lookups**; deleting the file forces exactly one rebuild query.
- Projection: image request pulls 2 fields and not the other image; the
  metadata endpoint, the detail endpoint and the gallery list all exclude the
  binary fields.
- Auth + headers: unauthenticated access to image/thumbnail/detail is refused;
  every image response is exactly
  `private, max-age=300, must-revalidate` + `Vary: Cookie` + `nosniff`, with no
  `public`.
- Gallery renders cards via the thumb route, with no inline `data:` URI,
  `loading="lazy"`, `decoding="async"` and the placeholder fallback present.

### 3.4 Two real bugs found and fixed during verification

1. **The cache check ran *after* the source guard** in
   `get_or_create_thumbnail()`, so a hit could not short-circuit without a
   source. Reordered so the cache is consulted first — this is what makes a
   hit free of database access.
2. **A leaked file handle**: `open(file_path, "rb").read(16)` had no context
   manager, and a failed atomic write could leave a stray `.tmp`. Both fixed.

### 3.5 Measured effect (fixtures matching production shapes)

| Scenario | Before | After | Change |
|---|---|---|---|
| Gallery page, 20 cards (processed images) | 4,229 B | 1,743 B | **−58.8%** |
| One modal open (JSON + 2 images) | 83,235 B | 62,555 B | **−25.0%** |

On real data the reduction is far larger: processed images are ~15 KB and
originals ~103 KB, while previews are ~1–3 KB. The 4,229 B figure above comes
from small solid-colour fixtures, which compress to almost nothing; it
understates the real-world gain by roughly an order of magnitude.

## 4. Not verified: live database

The Atlas cluster (`ac-dj2qbdh-shard-00-*`) failed to keep a primary for the
final ~40 minutes of work. Observed repeatedly:

```
No replica set members match selector "Primary()"
ac-dj2qbdh-shard-00-01.mongodb.net:27017: timed out
topology_type: ReplicaSetNoPrimary
```

It connected on some attempts and then failed on the first real query. Probing
with a 30 s server-selection timeout and a 20 s connect timeout also failed, so
this is a genuine cluster/network outage, not a client timeout being too short.
The app's own retry logic reported "All MongoDB connection attempts failed"
and fell back to read-only mode.

**Consequence:** the live-data suite (`ealpr_b6_live_readonly.py`, strictly
read-only) could not run. The checks below are therefore **outstanding, not
passed**:

- gallery rendering against the 66 real records
- byte-exact verification of a real stored original through the image endpoint
- real MIME sniffing on real data
- thumbnail generation and cache reuse on real data
- confirmation that the 60 `BinaryField` originals and the 6 path-backed
  records are still intact and unchanged
- re-confirmation of the collection counts (66 detections) after the run

Everything that does not require the database **was** verified (sections 3.1–3.3).
The Block A inventory of image storage (B1) was completed earlier against live
data and remains valid, and a live render during that window did produce 22
gallery cards with no empty state.
