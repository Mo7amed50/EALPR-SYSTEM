## 5. Failure Scenario Analysis

### 5.1 Unexpected Worker Exception

**Current behaviour: the consumer is extremely unlikely to die from an exception, and if it
somehow did, nothing would notice or react.**

The loop body is:

```python
while not _shutdown.is_set():
    try:
        job_id = _queue.get(timeout=0.2)
    except queue.Empty:
        continue
    if job_id is None:
        _queue.task_done(); break
    try:
        run_job(app, job_id)
    except Exception:
        log.exception(...)          # "belt and braces"
    finally:
        with _queue_lock: _queued_ids.discard(job_id)
        _queue.task_done()
        if _queue.empty(): _idle.set()
```

`run_job` is documented as never raising and the code agrees: its body is wrapped in
`try/except Exception` (lines 479-523) and its `finally` calls `_cleanup`, which has its own
`try/except Exception` (line 541-545). `process_license_plate` is also non-raising — all
failure modes return a `success=False` tuple, including the catch-all at `utils.py:251`.
So the inner `except Exception` at line 243 is close to unreachable defensive code.

Residual escape routes, all low probability:

| Route | Assessment |
|---|---|
| `BaseException` from `run_job` (`SystemExit`, `KeyboardInterrupt`, `GeneratorExit`) | Practically impossible in a worker thread |
| `_queue.get()` raising something other than `queue.Empty` | Effectively impossible |
| `_queue.task_done()` raising `ValueError` in the `finally` | Structurally reachable (get/task_done imbalance), escapes the `except` because that only wraps `run_job`. Low probability. |
| `_queue_lock` held indefinitely by another thread | Would **deadlock**, not crash. No such holder found. |

Answers to the specific questions:

- **Does Flask notice?** No. The consumer is a detached daemon thread; nothing is registered
  with Flask or Werkzeug.
- **Does MongoDB notice?** No. It is an ordinary TCP peer.
- **Is the worker marked dead?** No. Nothing records thread exit. `_worker_thread` keeps
  pointing at the dead object, and `_all_workers` keeps containing it until some *future*
  `_ensure_worker` call lazily purges it (lines 213-214).
- **Does the queue remain alive?** Yes. `_queue` is a process-global object and is unaffected
  by thread death. Any ids still in it remain there.
- **Are queued jobs stranded?** Yes — see 5.2.
- **Does any automatic restart occur?** No.

### 5.2 Silent Worker Death

**There is no health signal in production. This is stated explicitly.**

What exists:

| Mechanism | Exists? | Used in production? |
|---|---|---|
| `worker_is_running()` (`inference_jobs.py:898`) | Yes — `thread.is_alive()` | **No.** Referenced only at `tests/test_inference_jobs.py:1171,1180,1182` |
| Heartbeat / `last_seen` timestamp | **Does not exist** | — |
| Worker status document / field | **Does not exist** | — |
| Consumer liveness in any endpoint or log | **Does not exist** | — |
| `queue_depth()`, `queued_ids()` | Yes | `queued_ids()` is used internally by `recover_jobs` line 744. `queue_depth()` is tests-only. |
| `wait_for_idle()` | Yes | Tests-only |

`worker_is_running()` is the correct primitive and it is already written — it is simply never
called by anything except the test suite. This is the single most important structural fact
for C4: **the detection capability exists; only the caller is missing.**

**Stranding is possible, by three distinct routes:**

**(a) Consumer gone, backlog waiting, no new submission.**
If the consumer thread ends while ids sit in `_queue`, nothing restarts it until the next
`enqueue()` call reaches `_ensure_worker` (line 281). The jobs remain `queued` in Mongo.
`QUEUED_STALE_SECONDS` is applied *only inside* `recover_jobs()`, which runs **only at
startup**. There is no periodic sweep. So a live, healthy, serving process can hold `queued`
jobs indefinitely — and a client polling `GET /api/inference/jobs/<id>` sees `queued` forever
with no error.
*Partial mitigation, stated honestly:* the **next** submission calls `_ensure_worker`, which
starts a consumer, which drains the whole backlog including the stranded ids. So the system
self-heals on next activity. If the system is idle, nothing happens until a restart — and at
that restart the jobs are recent, so they are requeued and run normally.

**(b) Job already dequeued, consumer dies mid-`run_job` — the significant gap.**
`_queue.get()` has already removed the id. The job is `processing` in Mongo and is in no
in-memory queue. `recover_jobs()` will only fail it if it matches the stale-processing
predicate:

```python
started_at < processing_cutoff   OR   (started_at is None AND created_at < processing_cutoff)
```

`processing_cutoff = now - 600s`. Therefore a job that was `processing` when the process
died **less than 600 seconds before the restart** matches neither branch. It is not failed,
not requeued, and not in the queue. **It is permanently stranded until some later
`recover_jobs()` run happens at least 600s after its `started_at`** — i.e. typically a second
process restart.

This is realistic, not theoretical: a crash-and-immediately-restart is the single most
common deployment event, and it lands squarely in the 600s window. It is a **bug in C3's
recovery coverage**, not merely a supervision gap, and it is the highest-value finding in
this audit. It is documented here and deliberately **not** fixed in this audit-only block.

**(c) Recovery ran once, against a MongoDB that was down.**
`_initialization_done = True` is set at line 877, **before** `recover_jobs()` is called at
line 882. If Mongo is unavailable at that moment, `recover_jobs()` catches the error, sets
`counts["errors"] += 1`, and returns. The guard stays `True` forever, so recovery is never
retried in that process. Combined with (b), a `processing` job can sit indefinitely.

### 5.3 MongoDB Outage

Connection is established with `serverSelectionTimeoutMS=5000`, `socketTimeoutMS=5000`,
`retryReads=False`, `retryWrites=False` (`ealpr/__init__.py:177-186`).

| Event | Behaviour |
|---|---|
| **Claim fails** (`_claim`, line 449) | `findAndModify` raises → propagates out of `run_job`? No: `_claim` is called at line 468, which is **outside** the `try` that begins at line 479. So the exception propagates out of `run_job` to the `except Exception` in `_worker_loop` (line 243), which logs and continues. The job stays `queued`. **No status change, no `error_code`.** The id is already out of the queue, so it is now in state (b) from 5.2 — stranded, though still `queued`, so a later recovery would requeue it if younger than 1800s. |
| **Job document save fails** (`_mark` → `job.save()`, line 357) | Raises → `run_job`'s `except Exception` → `_fail(job, ERROR_INTERNAL, exc)` → which calls `job.save()` **again** and raises again. That second raise escapes `run_job` (it is raised inside the `except` handler) → caught by `_worker_loop` line 243. Worker survives. Job remains in its last successfully-written state. |
| **Inference finishes, `_persist_detection` fails** | Caught explicitly at lines 510-518 → `_fail(job, ERROR_PERSIST, db_err)`. Job becomes `failed` with a sanitised message. If Mongo is still down, that `_fail` save also fails and the job is left `processing` — see section 6. |
| **Can the worker continue?** Yes. Every path above is contained; the loop continues to the next id. |
| **Can the worker die?** Not from Mongo errors. All are `Exception` subclasses caught by line 243. |
| **Visitor lookup during outage** | `_resolve_visitor` is fail-soft (lines 390-403): a DB error prints and returns `status="unknown"`, so the detection is still created. Intentional and correct. |
| **`DB_ENABLED=False` at boot** | `recover_jobs` returns zeros (line 696-698); `run_job` skips `_persist_detection` (line 509) and completes with `detection=None`; the POST endpoint is blocked by `@db_required`. |

Note the asymmetry at step 26/27: when Mongo fails *between* the detection insert and the job
completion, the job can be left `processing` with a `DetectionResult` already written. No
duplicate is created, but job and detection disagree. This is a pre-existing consistency gap,
not introduced by supervision, and is recorded in section 17.

### 5.5 Application Restart

This is the scenario where C3 already does real work, and where the audit found the gap in
5.2(b).

```
process N dies  ──┬── jobs still `queued`     → in-memory queue lost, Mongo says queued
                  ├── jobs `processing` <600s → NOT matched by stale predicate → STRANDED  ⚠
                  ├── jobs `processing` >600s → failed `stale_processing` ✅
                  ├── jobs `completed`/`failed` → untouched ✅
                  └── staged files            → orphan sweep, if age > 1800s ✅

process N+1 boots
  → create_app → initialize_inference_jobs (one-shot)
  → recover_jobs: requeue recent runnable, fail the rest
  → _ensure_worker ONLY IF counts["requeued"] > 0
```

Two convergence problems:

1. **The `processing` < 600s hole (5.2b).** Not convergent. The job is neither run nor failed.
   Only a later `recover_jobs()` at ≥600s resolves it, and `recover_jobs()` only runs at
   startup. So it can persist across many process lifetimes.
2. **No consumer when nothing was recovered.** If `counts["requeued"] == 0`, `_ensure_worker`
   is not called (line 887-889) and no worker thread exists. This is intentional lazy-start
   from C2 and is not a defect — the next submit starts it. But it means "is the worker
   running?" is legitimately `False` at idle, so **any C4 health check must not treat
   "no worker" as a fault on its own**; it must be "no worker *while work is outstanding*".

Positive verification: the in-memory queue and Mongo state **do** converge safely for
`queued` jobs. Requeue is by `job_id`, and `_claim` re-reads Mongo atomically, so even if the
same id somehow appeared twice in `_queue`, the second `get` would find `status != queued`,
`_claim` returns `None`, and `run_job` logs "already in state" and returns without running
(verified by `test_concurrent_runners_cannot_both_claim_a_job` and
`test_failed_job_is_never_rerun`).

### 5.6 Multiple Consumers

If a second consumer somehow appeared, the consequences are bounded by the atomic claim:

| Property | Behaviour |
|---|---|
| Two consumers, same `job_id` in queue | **Exactly one** wins. `_claim` is `findAndModify` filtered on `status=queued`; the loser gets `None` and returns without running (`inference_jobs.py:469-477`). |
| Two consumers, different `job_id`s | Both run, **but** `process_license_plate` takes `INFERENCE_LOCK` internally, so inference still serialises. No correctness loss. |
| Duplicate `DetectionResult` | **Not possible** from concurrent consumers. Covered by `test_concurrent_runners_cannot_both_claim_a_job` and `test_13_no_duplicate_detection_is_created`. |
| Structural prevention | `_ensure_worker` (lines 212-228) holds `_queue_lock` across the registry check *and* thread creation, and reuses any live registered thread. C3's `_all_workers` makes "at most one consumer" structural. Covered by `test_c3_12_exactly_one_consumer_exists` and `test_c3_12b_repeated_initialization_does_not_multiply_threads`. |

**C3's one-consumer invariant is sound and must be preserved by whatever C4 adds.** A
supervisor that starts a worker without going through `_ensure_worker` would break it.

**Hazard — the reloader.** `use_reloader=False` (line 18 of `app.py`) is currently what keeps
one process. If anyone enables `debug`-driven reloading or runs under a multi-process WSGI
server, each process gets its own module state: its own `_initialization_done`, its own
`_queue`, its own consumer. `create_app` would then run recovery in every process and
re-queue the same `job_id`s into several independent queues. **Duplicate execution would
still be prevented by the atomic claim**, so the consequence is redundant work and repeated
consumer threads, not corrupted data. This is the correct safety property to rely on, and it
is why a process-level supervisor (Option C) is safe to recommend.

### 5.7 Worker Restart

A restart is **mechanically already supported**. `_ensure_worker` starts a new consumer
whenever no live one is registered (lines 215-228). What is missing is anything that *calls*
it. Restart safety analysis:

| Property | Safe? | Why |
|---|---|---|
| Two consumers at once? | Yes | `_ensure_worker` reuses a live thread; only creates when none is alive |
| Re-running an in-flight job? | **Yes, safe** | The id was removed from `_queue` by `get()`. A restarted consumer cannot see it. And `_claim` refuses any job whose status is not `queued`, so even a re-queued `processing` job would be rejected. |
| Re-running a queued job? | Safe — and *correct* | A `queued` job that is still in `_queue` was never claimed, so running it is exactly right. |
| Thread leak across restarts? | No | `_ensure_worker` purges dead entries (lines 213-214) before adding. Repeated restarts do not accumulate threads. |
| `INFERENCE_LOCK` contention? | No | New consumer constructs no models; `plate_detection_model` is a module global and stays loaded. C3.7's `_MODEL_LOAD_LOCK` is irrelevant here. |

**Conclusion: restarting the consumer thread cannot create duplicate business side effects.**
The one thing it must never do is re-queue `processing` jobs — see section 6.

## 6. Duplicate-Execution Risk

### The trace

```
InferenceJob(status=queued)
      │  _claim()  — findAndModify, filter status=queued        inference_jobs.py:437
      ▼
InferenceJob(status=processing, started_at=T, attempts+1)
      │
      │  process_license_plate()  (INFERENCE_LOCK held)         inference_jobs.py:493
      │  _resolve_visitor()  → sets entry_datetime_utc if empty  inference_jobs.py:506
      │  _persist_detection()  → record.save()  ◄── WRITE #1      inference_jobs.py:511 / 428
      ▼
      │  _complete()  → _mark() → job.save()    ◄── WRITE #2      inference_jobs.py:520 / 528
      ▼
InferenceJob(status=completed, detection=<ref>)
```

**WRITE #1 and WRITE #2 are separate Mongo writes with no transaction.**

### The dangerous window

Between `record.save()` (line 428) and `job.save()` (line 530) the system is in this state:

```
InferenceJob:  processing        ← not terminal
DetectionResult: EXISTS           ← business record already committed
```

A crash, process kill, or unrecoverable DB error in that window leaves exactly this. The
detection is real and visible in the gallery; the job is stuck non-terminal.

**Any mechanism that retries such a job creates a second `DetectionResult` for one image** —
duplicate gallery entries, duplicate counts, wrong analytics. This is why C3 chose to **fail**
stale processing jobs rather than requeue them, and that decision is correct and must be
preserved verbatim.

### Does a worker restart trigger this window?

**No.** Three independent reasons:

1. The id was already removed from `_queue` by `get()`; a restarted consumer never sees it.
2. `_claim` filters on `status=queued`; a `processing` job can never be re-claimed.
3. A restarted consumer only picks up ids still physically in `_queue`, which are by
   definition un-claimed `queued` jobs.

**So restarting the consumer is duplicate-safe. What is NOT safe is a naive "requeue anything
non-terminal" recovery.** That is the one thing C4 must not do, and the one thing a
supervisor must be forbidden from doing.

### Visitor side effect

`_resolve_visitor` (line 396-401) sets `entry_datetime_utc` only `if not
visitor.entry_datetime_utc`. It is therefore **effectively idempotent** — a retry would find
the field already set and do nothing. No duplicate visitor row is possible from the job path
either; `Visitor` is only ever *read* and *mutated in place*, never created. (Visitor creation
is a separate, authenticated path outside this subsystem.)

### Existing protection summary

| Protection | Present | Location |
|---|---|---|
| Atomic single-winner claim | Yes | `_claim`, line 437-459 |
| Re-claim of non-`queued` refused | Yes | line 449-451 filter |
| Duplicate queue entries harmless | Yes | `_claim` returns `None`, line 469-477 |
| Stale `processing` never retried | Yes | `recover_jobs` line 768-780 fails, never requeues |
| Detection created before job completed | **Yes — the window** | lines 428 vs 530 |
| Idempotency key for retry | **No** | nothing in the schema |

**Interaction with worker startup — the gap.** `initialize_inference_jobs` starts a consumer
only when `counts["requeued"]` is truthy (lines 887-889). Combined with the one-shot guard set
*before* recovery runs (line 877), the consequences are:

- Recovery that finds nothing → no consumer. Correct (lazy start), but means a C4 health check
  must key on "outstanding work" not "thread alive".
- Recovery that errored → guard already set → never retried in this process.
- Recovery that left a sub-threshold `processing` job → that job is silently skipped, and
  because `counts["requeued"]` may be 0, no consumer starts either.

## 10. Supervision Architecture Options

### Option A — In-Process Health Monitor

A lightweight monitor that periodically compares outstanding work against worker liveness and
calls `_ensure_worker` when they disagree.

**Fit: strong.** The worker is in-process, so in-process monitoring is the only mechanism
that can see a dead thread in a live process. All the primitives already exist:
`worker_is_running()` (line 898) is written and correct; `_ensure_worker` (line 202) already
implements create-or-reuse under a lock; `queue_depth()` and `queued_ids()` (lines 285, 290)
already expose the outstanding-work side of the comparison.

**Duplicate safety: proven safe in section 5.7.** Restart cannot re-run a `processing` job
because `_claim` filters on `status=queued`.

**Cost:** one more thread, one timer, and a new decision about what "outstanding work" means
(queued-in-memory only? or also non-terminal Mongo jobs?).

**Risk:** it can only observe thread liveness. It cannot detect route 5.2(b) — a `processing`
job with no consumer is invisible to a liveness check unless the monitor also *counts*
non-terminal jobs, and that count is only meaningful with an age bound.

### Option B — Application Supervisor

A supervisor thread owning the worker's whole lifecycle, restarting it on a fixed schedule
regardless of health.

**Fit: weak.** It is Option A with more machinery and a worse failure mode: a periodic
restart interrupts in-flight work, and a supervisor that restarts too eagerly would burn CPU
reloading state for no reason. It also duplicates logic `_ensure_worker` already owns. Nothing
in the evidence justifies replacing a working lock-guarded creator with a second authority.

**Not recommended.** If a monitor is built, it should *call* `_ensure_worker`, not compete
with it.

### Option C — Deployment-Level Supervisor

A process manager (Windows Service / NSSM, `systemd`, Docker `restart: always`, or a
Waitress/Gunicorn service wrapper) that restarts the process when it exits.

**Fit: complementary, not a substitute.** It addresses process death — the realistic failure
mode — but it is **blind to a dead thread in a live process**, which is the actual C4 gap.
A process manager would also have re-run recovery on every restart, which is exactly the
scenario that exposes the 5.2(b) stranding hole.

**Current state, from evidence:**
- `requirements.txt` has **no WSGI server** — no Waitress, no Gunicorn.
- `app.py` uses `socketio.run(..., allow_unsafe_werkzeug=True)` — the Flask **development
  server**, with `debug=True`, in every environment.
- No service wrapper, no container definition, no restart policy was found.
- The app is currently started as a bare `python app.py`.

**Local development vs production — explicitly distinguished:**

| | Local development | Production deployment |
|---|---|---|
| How it runs | `python app.py`, Werkzeug dev server, `debug=True` | Same command today — there is no separate production entry point |
| Process manager | none | none |
| Restart on crash | manual | manual |
| Realistic failure mode | developer restarts | unattended process death, unattended restart never happens |
| Option C fit | unnecessary — the developer is the supervisor | **worthwhile, and cheap** |

The absence of any production WSGI server and of `debug=False` is a real operational risk, but
it is **deployment configuration, not worker supervision**, and changing it would violate this
block's scope boundary. It is recorded in sections 15 and 17.

### Comparison

| | Sees dead thread | Sees dead process | Duplicate-safe | New surface | Addresses 5.2(b) |
|---|---|---|---|---|---|
| A — in-process monitor | ✅ | ❌ | ✅ proven | 1 thread + timer | Only if it counts aged jobs |
| B — supervisor thread | ✅ | ❌ | ⚠️ interrupts work | 1 thread + restart logic | ❌ |
| C — process manager | ❌ | ✅ | ✅ (claim) | 0 app code | ❌ (triggers it) |

**None of the three alone fixes 5.2(b).** That is a recovery-logic gap, not a supervision gap,
and C4 must address it explicitly if it is to claim runtime reliability.

## 11. Recommended C4 Implementation Boundary

**Recommended: Option A (minimal in-process health monitor) + a bounded fix to recovery
coverage, with Option C documented as a complementary deployment change that is out of this
block's scope.**

**In scope for C4 implementation:**

1. **Health observation** — call the existing `worker_is_running()` from one place and combine
   it with `queue_depth()`/`queued_ids()` to form a single `worker_health()` fact. No new
   primitive is needed; the audit's finding is that the primitive exists and has no caller.
2. **Conditional restart** — when work is outstanding and no live consumer exists, call
   `_ensure_worker(app)`. Reuse the existing function; do not add a second consumer-creation
   path, so C3's one-consumer invariant is preserved by construction.
3. **Bounded restart** — cap restarts per unit time so a persistent fault cannot become a
   thread-churn loop.
4. **Close the 5.2(b) stranding hole** — a `processing` job older than a short "no consumer can
   be running this" bound, or a `processing` job found at startup with no live consumer, must
   become terminal. It must **not** be requeued. This is a recovery-logic change and is the
   single highest-value item in this block.
5. **Diagnostics** — a read-only health surface (log line and/or a function) so an operator can
   see worker state. No new public endpoint unless separately approved.
6. **Recovery retry** — do not set `_initialization_done = True` before recovery succeeds, or
   re-arm the guard on failure, so a startup Mongo outage does not permanently disable
   recovery for that process.

**Explicitly stated limitation.** If C4 is scoped to *only* thread supervision, then
**automatic in-process restart alone does not make the subsystem reliable**, because route
5.2(b) strands work without any dead thread at all. The audit states this plainly rather than
implying that a watchdog closes the gap. A watchdog fixes symptom (a); items 4 and 6 fix the
causes in (b) and (c).

**What must not change:** the claim, the failure policy, the thresholds, retention, the AI
pipeline, `INFERENCE_LOCK`, and the recovery decisions themselves. In particular, **no
mechanism may requeue a `processing` job.**

## 15. Security Assessment

Assessed specifically for a supervision/restart design. **No change was made.**

| Concern | Assessment |
|---|---|
| **Duplicate execution** | Prevented by `_claim`'s atomic claim, which C4 restart does not weaken (section 6). The real duplicate risk is a retry of a `processing` job — C4 must not introduce one. |
| **Job enumeration** | No new endpoint is proposed. The existing `GET /api/inference/jobs/<id>` returns 404 (not 403) for non-owners, deliberately, to prevent id probing (`blueprints/inference.py:120-126`). A health endpoint must not expose job ids, counts by user, or `image_path`. |
| **Unauthorised job control** | A restart capability must never be reachable from HTTP. It belongs in-process, called from the startup hook and a timer — no route, no admin toggle. A "restart worker" endpoint would be a denial-of-service primitive. |
| **Unsafe filesystem cleanup** | C3's `recover_staged_artifact` requires the exact regex *and* proven non-ownership *and* an age margin. C4 must not add a restart path that triggers cleanup with weaker conditions. Restarting the consumer does not touch the filesystem at all. |
| **Race conditions** | `_ensure_worker` serialises under `_queue_lock`; the recovery requeue path takes the same lock. A monitor must call `_ensure_worker`, never create a thread directly, or it can race the registry and produce two consumers — the exact bug C3 fixed. |
| **Unbounded threads** | **The one genuine new risk.** `shutdown()` deliberately leaves an unjoinable worker registered rather than forgetting it (lines 338-341). A supervisor that repeatedly "restarts" on a thread it cannot kill would accumulate threads, each holding an `app_context`. Restart must be gated on `not thread.is_alive()` **and** capped per unit time. |
| **Resource exhaustion** | A restart loop could thrash CPU and re-read staged images. Bounded restarts and a health check that requires *outstanding work* (not merely a dead thread) prevent the no-work case from ever triggering. |
| **Process instability** | `app.py` runs `debug=True` with `allow_unsafe_werkzeug=True`, exposing the Werkzeug interactive debugger. A monitor does not change this, but it is a **pre-existing production risk** worth flagging to whoever owns deployment. Fixing it is out of C4 scope. |
| **Log/secret exposure** | Health logs must carry `job_id` at most — never `image_path`, plate text, or exception text — matching C3's existing discipline (`_fail` logs the real exception server-side, stores only safe prose). |

|---|---|---|

| Warm sync `/process_plate` | C2 | 2.360 s |

Design implications for C4, all derived from these numbers and the code — **no new numbers are
invented and no throughput claim is made**:

- **Health-check cost is a count, not a query against the collection.** `queue_depth()` and
  `queued_ids()` are in-memory. A monitor driven by them needs no Mongo round-trip, so Atlas
  latency does not enter the loop. A monitor that instead queried `InferenceJob` each tick
  would add a network round-trip per tick for a process whose measured warm inference is
  2.360 s — the wrong trade.
- **The `_claim` extra round-trip is already the design.** Adding supervision must not add a
  Mongo round-trip to the per-job path; it is not needed and would tax the 2.360 s budget.
- **Restart is not free but is rare.** Restarting a consumer constructs no models
  (`plate_detection_model` is a module global), so a restart costs one thread start, not a
  reload. This is why restart is safe to do on a moderate interval.
- **The `processing` staleness bound is the risky constant.** `PROCESSING_STALE_SECONDS = 600`
  is ~150× the measured warm inference — deliberately generous. Any *new*, shorter bound
  introduced to close 5.2(b) would be **new evidence-free territory** and must be justified
  against the 2.360 s figure, or made conditional on "no live consumer exists" rather than on
  elapsed time alone.
- **No throughput improvement is claimed or implied.** `INFERENCE_LOCK` still serialises all
  inference, so job throughput remains one job at a time regardless of how many consumers
  exist.

## 18. Proposed C4 Implementation Plan

Ordered by value. Items 1 and 2 are the substance; 3-6 are hardening.

**Phase 1 — close the real defect (highest value, smallest change)**
1. **Resolve sub-threshold `processing` jobs.** Add to `recover_jobs` a rule: a `processing`
   job found at startup, when **no live consumer exists**, is failed as `stale_processing`
   regardless of age. Rationale: after a restart there is by definition no worker that could
   own it, so its age is irrelevant. It must be **failed, never requeued** — requeueing is the
   one action that could duplicate a `DetectionResult` (section 6). Requires no schema change.
2. **Re-arm recovery after a failed attempt.** Move `_initialization_done = True` to *after*
   a successful `recover_jobs()`, or clear it on `counts["errors"]`, so a startup Mongo outage
   does not disable recovery for the process lifetime.

**Phase 2 — supervision (Option A)**
3. **Add `worker_health()`.** Compose existing primitives: returns worker liveness, queue
   depth, and whether outstanding work exists. No Mongo round-trip.
4. **Add a monitor that restarts conditionally.** Start it from `initialize_inference_jobs`
   after recovery. Logic: if `queue_depth() > 0` and `not worker_is_running()`, call
   `_ensure_worker(app)`. Must call the existing function, never create a thread.
5. **Bound the restart rate.** Cap restarts per interval, log when the cap is hit, and never
   restart when there is no outstanding work.

**Phase 3 — observability and shutdown**
6. **Log health transitions** — worker start, worker exit, restart, cap hit — with `job_id`
   only, never paths or plate text.
7. **Consider an `atexit` hook** calling `shutdown()` so a clean interpreter exit does not
   abandon queued work. Judged low priority: C3 recovery already requeues on restart, and a
   daemon thread is killed regardless. Should be an explicit decision, not an accident.

**Explicitly not in C4 implementation:** process-manager deployment, WSGI server, `debug`
flag changes, periodic artifact sweeping, video/camera work, schema changes.

## 20. Final Audit Verdict

**C3's job-state machine is sound and was verified against the code with no discrepancy
found.** The atomic claim, the sanitised failure codes, the ownership-based artifact cleanup,
the terminal-only TTL retention, and the one-consumer invariant are all correctly implemented
and well tested. Nothing in C3 needs to be redone.

**The reliability gap is real, but it is not the one the brief anticipated.** The consumer
thread is very unlikely to die from an uncaught exception — `run_job` cannot raise,
`process_license_plate` cannot raise, and the loop has a further `except Exception` net. What
actually happens is **silent stranding**: work that reaches a non-terminal Mongo state with no
consumer and no mechanism to resolve it, while the process keeps serving traffic and every
health signal reads normal.

**The highest-value finding is a genuine defect, not merely a supervision gap: a job left
`processing` less than 600 seconds before a restart matches neither branch of the stale-
processing predicate, so recovery silently skips it and it stays non-terminal until some
later restart at least 600 seconds afterwards.** C3's own test suite cannot see this, because
every stale-processing test uses a job *older* than the threshold. Fixing this is worth more
than any watchdog, and it requires no schema change, no new dependency, and no architectural
change.

**Recommended boundary: Option A — a minimal in-process health monitor built on the
`worker_is_running()` primitive that already exists and simply has no production caller,
combined with a bounded fix to recovery coverage, and an explicit statement that a watchdog
alone does not close the stranding gap.** Option C is a worthwhile complement for process
death but cannot see a dead thread, and this audit does not propose deployment changes.

**Duplicate-execution safety is already established and must be preserved verbatim:** a
worker restart cannot re-run an in-flight job, because the id has already left the queue and
`_claim` refuses any job that is not `queued`. The one forbidden action is requeueing a
`processing` job, because the `DetectionResult` insert and the job completion are two separate
Mongo writes with no transaction between them.

**The audit created one file, modified no application code, mutated no data, and started no
implementation.**
